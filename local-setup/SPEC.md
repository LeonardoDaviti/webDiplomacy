# webDiplomacy Local LAN Instance — Spec

**Date:** 2026-09-20
**Status:** Current. Supersedes the draft; corrected against `master @ 7be9bb05` (version 1.83).

> Every architectural claim below was checked against this checkout. Where the draft spec said
> something that is not true of this codebase, the corrected statement is here and the draft is
> void. If you find a claim here that the code contradicts, fix this file in the same change.

---

## Problem Statement

Two friends want to play Diplomacy against each other, and occasionally with a handful of
invited guests, on a private network at home. They are not looking for a public community, a
ladder, or strangers. What they want is:

1. **Variant breadth.** Not just Classic. Ancient Mediterranean, Colonial, Modern, Cold War,
   Empire, Chaos, and as many of the long tail of community maps as can reasonably be made to
   run — dozens, not a handful. Trying a new map should be a ten-minute job, not a project.
2. **Westeros.** A Game of Thrones map is specifically wanted. It is not offered by the sites
   they can otherwise use.
3. **Custom art.** The owner wants the freedom to reskin a map — at minimum Classic — with his
   own artwork, for the pleasure of playing on a board he made.
4. **Two-player play that actually works.** Most evenings there are exactly two humans. That
   means either genuinely two-player maps (France vs Austria, Germany vs Italy, Cold War) or
   filling the empty chairs with bots.

No public service gives all four at once. The large public sites have breadth but no custom
art and no Westeros; the small ones have odd variants but no bots and no control over the
install; and none of them let the owner put his own map file on the server. Running the
software privately is the only way to get all four, and webDiplomacy is AGPL, so running it
privately is permitted and supported.

The secondary problem is that this must be **low-maintenance**. It runs on a machine in the
owner's house. It must survive reboots, must not lose game state, must be reachable from a
phone on the sofa, and must not quietly become a public server by accident.

---

## Solution

Run upstream webDiplomacy 1.83, unmodified, in the Docker Compose stack that ships with it,
on a single machine on the home LAN.

- **Deployment shape.** The stack's `core` profile (database, web server, PHP runtime, event
  server, cache) plus the `dev` profile (mail catcher, database admin UI) during setup. The
  web tier is opened to the LAN subnet only; every other published port stays bound to
  localhost on the host. No TLS, no public DNS, no port forwarding.
- **Accounts.** Public self-registration is switched off at the web-server level. Ten accounts
  are created by hand through the admin control panel — one owner/admin, one for the friend,
  and eight spare for guests — with passwords generated by the admin tools and written down
  once in a gitignored file. There is no e-mail delivery to speak of, so the mailer is put in
  its debug mode where the message body is printed rather than sent.
- **Variants.** Fourteen variants already ship in this checkout; nine are switched on by
  default and five more are present but not registered. The rest are harvested from the
  vDiplomacy family of community variants, in supervised waves, and registered in a local ID
  registry so that two ports never collide.
- **Westeros.** Taken from the `mcoirad/gameofthrones-diplomacy` port, which is a webDiplomacy
  variant package of the same shape as the ones in the tree. It requires a dependency variant
  to be installed first.
- **Bots.** The no-press bot pack lives in its own separate checkout, not in this stack's
  compose file. It joins the stack's Docker network and plays through the site's API with
  pre-created bot accounts. Bots play **Classic gunboat only**; their models are trained on the
  Classic map and they are configuration-limited to a short list of variant IDs.
- **Board.** Ported variants, Westeros, and any map reskin are played on the **legacy board**,
  not the React board. This is a hard constraint, explained under Implementation Decisions.

## User Stories

### Owner (runs the machine)

1. As the owner, I want to bring the whole site up with one command on a freshly booted
   machine, so that a power cut does not cost me an evening.
2. As the owner, I want the site to come back by itself after a reboot without me typing
   anything, so that I do not have to be at the machine to play.
3. As the owner, I want a single URL I can check that tells me whether games are processing,
   so that I do not discover a stalled gamemaster three days into a game.
4. As the owner, I want the database to survive the containers being rebuilt, because the
   stack as shipped throws the database away when its container is recreated.
5. As the owner, I want a nightly backup written outside the repository, so that a bad
   `git clean` does not take the games with it.
6. As the owner, I want to have restored from that backup at least once, on purpose, so that I
   know the backup is real.
7. As the owner, I want the site reachable at a stable address on my LAN, so that bookmarks on
   the phones keep working after a router reboot.
8. As the owner, I want the site reachable **only** from my LAN, so that I have not
   accidentally published a server with a known default database password.
9. As the owner, I want a written runbook for restart, health check, restore, and adding a
   variant, so that I can do those things a year from now without re-deriving them.
10. As the owner, I want a written upgrade procedure, because the site bricks every page when
    the database schema version and the code version disagree.
11. As the owner, I want a registry of which variant owns which numeric ID, so that installing
    a new map never silently overwrites an existing one.
12. As the owner, I want to add a variant by dropping a folder in and flipping one config
    entry, with no database surgery.
13. As the owner, I want to know, before I run a downloaded variant's code, that it is not
    doing anything hostile, because a variant is PHP that the site executes.
14. As the owner, I want the credentials file kept out of version control, so that pushing the
    branch somewhere never leaks the accounts.

### Player (the friend, and the owner playing)

15. As a player, I want to open the site on my laptop or my phone on the home Wi-Fi and see
    the game list, without a VPN or a client install.
16. As a player, I want to stay logged in across days, so that I am not typing a password every
    time I check a game.
17. As a player, I want private press — in-game messages to one named opponent that nobody
    else can read — because that is the game.
18. As a player, I want to choose from a long list of variants when I create a game, so that we
    can play something new on a whim.
19. As a player, I want to see a variant's starting position and know it matches the map it was
    ported from, so that I am not playing a broken port.
20. As a player, I want to play Westeros with exactly two of us, because that is a map we
    specifically want.
21. As a player, I want two-player Classic-derived maps (France vs Austria, Germany vs Italy,
    Cold War) available, for a quick evening game.
22. As a player, I want empty chairs in a seven-player Classic game filled by bots, so that two
    humans can play a full-size board.
23. As a player, I want orders I submit from my phone to be accepted, so that the LAN access is
    not read-only in practice.
24. As a player, I want the board to update when the other player's orders come in, without me
    reloading the page.
25. As a player, I want a phase that has finished to adjudicate promptly, rather than waiting on
    a cron job that runs once an hour.
26. As a player, I want build and retreat phases to resolve correctly on every variant we play,
    not only on Classic.
27. As a player, I want supply-centre counts after autumn to match what the map says, so that I
    can trust the scoreboard.
28. As a player, I do not want a ranking system telling me I am losing points, because there is
    no meaningful ladder among two friends.

### Guest (invited occasionally)

29. As a guest, I want to be handed a username and password that already works, rather than
    signing up, because signup is switched off.
30. As a guest, I want to join a game already in progress in the lobby without needing admin
    rights.

### Admin (the owner wearing the other hat)

31. As an admin, I want my own account promoted to moderator and admin, because the built-in
    self-promotion route does not work on this stack.
32. As an admin, I want to create and password-reset accounts from the web interface rather
    than by hand-writing SQL.
33. As an admin, I want to force the variant list and its caches to refresh after installing a
    map, so that a new variant actually appears.
34. As an admin, I want to see the raw content of a password-reset or registration e-mail that
    the site "sent", because nothing actually delivers mail here.
35. As an admin, I want to pause game processing while I am doing maintenance.

### Bot operator

36. As a bot operator, I want to know the hardware the bot pack needs before I commit to
    running it, because the models may not fit this machine.
37. As a bot operator, I want the bots to join only the games I intend, not every open game on
    the site.
38. As a bot operator, I want the bots restricted to maps they were trained on, so that they do
    not play nonsense on Colonial.
39. As a bot operator, I want to stop the bots without stopping the site.

## Implementation Decisions

### Runtime and topology

The site runs from the Compose file that ships in the repository. Its profiles are:

- **`core`** — the database (MariaDB 10.6), the web server (nginx), the PHP runtime (php-fpm
  8.4), the event server (Node 20), and the cache (Redis). This is the site.
- **`dev`** — a mail catcher and a database admin UI, both useful during setup.
- **`build`** — a one-shot container that compiles the React board, which is not in git and so
  is missing from a fresh checkout.
- **`reactdev`** — a hot-reloading React dev server, not used here.

There is **no `bots` profile**; the draft spec invented one. The web tier is **nginx in front of
php-fpm**, not Apache; any instruction phrased in terms of Apache modules, `.htaccess` or
virtual hosts does not apply.

**Nothing needs installing on the host but Docker.** PHP dependencies are installed by Composer
*inside* the PHP container by its entrypoint script on every start. There is no host PHP, no
host Composer, no host Node.

### Persistence — the one thing that must be changed on day one

As shipped, the database container has **no volume behind it**: only bind mounts of the source
tree. Deleting or recreating that container destroys the database, and the next start silently
reinstalls a blank one from the full-install SQL plus the bot-account SQL (both idempotent —
the installer checks whether the users table already exists). That is correct behaviour for a
throwaway dev stack and catastrophic for a live game server.

**Decision:** before any real game is created, the database gets a named Docker volume, and a
scheduled dump is written to a directory **outside the repository working tree**. A restore is
performed once, deliberately, to prove the backup. This is issue 002 and it gates everything
else.

### Game processing

Games do not process from a host cron job. The **event server container also runs the
gamemaster loop**: it calls the gamemaster endpoint roughly once a second over the internal
Docker network, using a URL and a shared secret it reads from an environment file. That file is
not in git; the PHP container's entrypoint regenerates it on every start from the secrets in
the site config. Consequences:

- Processing latency is seconds, not minutes. Phases resolve promptly, which is what the
  players want.
- If the event container is down, **nothing processes at all**, and the site looks fine.
- If the site config lacks a gamemaster secret, the loop authenticates against nothing and
  processing never happens.

**Health checks, in increasing order of effort:** the site's status endpoint, which reports the
gamemaster's last run time out of the cache; the entrypoint's log file, served as a static text
file, whose success marker is the line `READY - webDiplomacy system initialized`; and the
event container's own logs, which show each gamemaster call.

### Secrets

The PHP entrypoint fills in **only** the event-server secret. The general-purpose secret, the
salt, the JSON API secret and the gamemaster secret are all **empty in the sample config** and
stay empty unless set by hand. They must all be set before the site is used — an empty
gamemaster secret in particular means no games process. The database password defaults to a
value published in the compose file; it is changed as part of opening the site to the LAN.

### Making the site admin

The documented "visit the gamemaster endpoint with the secret and get promoted" route
**does not work on this stack**. It only promotes while the site has never processed a turn,
and the event server's loop processes within seconds of first start, closing the window before
a human can use it. Promotion is therefore done in SQL, which the install notes already
document as the alternative:

```sql
UPDATE wD_Users SET type='User,Moderator,Admin' WHERE type='User';
```

Run it when exactly one account exists — the owner's.

### Accounts and registration

Accounts are created through the admin control panel: a create-user action (which does not set
a password), a password-reset action (which prints a freshly generated random password on the
page), and a change-email action. There is **no "e-mail verified" flag** in this schema, so
nothing has to be faked. An alternative route generates a registration link containing a token,
which can be handed to a guest directly.

Mail: the mailer has a debug mode which prints the message to the page instead of sending it —
that is the simplest way to read a reset mail. The `dev` profile's mail catcher also works and
is nicer when several messages are involved.

Registration itself is protected by a map-based puzzle. There is no reCAPTCHA and no SMS step
in this codebase, and the OAuth and SMS integrations are inert. **There is no configuration
flag that disables registration.** The site's panic switch would do it but also stops game
processing, which is unacceptable. **Decision:** public registration is blocked in the
**web-server configuration**, by refusing the registration URL (and its directory form) before
it ever reaches PHP. Browser fingerprinting in this codebase is passive and makes no external
requests, so there is nothing to switch off for privacy.

### Scoring

Points cannot be turned off by configuration; they are structural. Ghost Ratings **can** be
turned off with a config flag, and are, since a two-person ladder is meaningless. Story 28 is
therefore satisfied only in part, and deliberately so.

### Variants — how they work here

A variant is a folder containing a variant definition class, an installer, a `classes/`
directory of variant-specific overrides, and a `resources/` directory. The mandatory stylesheet
is `resources/style.css` (**not** `variant.css`, as the draft claimed), alongside a dark-mode
resources directory. Some variants additionally ship an interactive-map directory with a small
map thumbnail; the draft's claim that no such directory exists in this codebase **is wrong** —
four variants in the tree have one. A `cache/` directory is gitignored and must exist and be
writable.

A variant becomes available by being listed in the site config's variant array, keyed by its
numeric ID. On first load the loader **auto-installs** it, running its installer against the
database. After adding variants an admin must run the variant-info update action, and the
variant-wipe action to clear caches, before they appear.

The variant base class and loader have been stable: the variant API version is still 1 and the
base class has not changed in three years. The real porting risk is **PHP 8.4 compatibility in
the variant's own classes**, plus the autoloader change — not API drift.

**ID registry rules:**

- Every variant has two numbers: its own ID and the map ID its geography is installed under.
  Derivative variants reuse a parent's map ID (four of the Classic derivatives in the tree share
  map ID 1) — that is normal and must not be "fixed".
- IDs already used in this tree are reserved forever, whether or not the variant is enabled.
- **ID block 900 and above is reserved for renumbered ports**: when a harvested variant's
  upstream ID collides with one already in use, it is renumbered into 900+ rather than
  displacing the incumbent. The registry file records the original ID alongside the new one.
- Nothing is installed before its row exists in the registry.

### Harvest waves — recomputed

The draft's waves assumed an empty tree. The tree is not empty: **fourteen variants are already
present** and nine of them are already enabled. The draft's "wave 1" Chaos and Build-Anywhere,
and its "wave 2" Cold War, France-vs-Austria and Germany-vs-Italy, are all **already here** and
need no harvest at all. Recomputed:

- **Wave 0 — zero harvest, config only.** The five variants that are present in the tree but not
  registered: Build Anywhere, Fleet Rome, Custom Start, Colonial, Zeus 5. Adding their IDs to the
  config array and refreshing the variant info is the entire job. Do this first: it is the
  cheapest possible test of the whole add-a-variant pipeline, on code that is already known
  good.
- **Wave 1 — the two named wants.** Westeros, and confirming the two-player roster. Both have
  their own issues.
- **Wave 2 — supervised harvest.** Community variants from the vDiplomacy family, taken in
  batches, each given a fixed triage budget: if it does not load and show a correct starting
  position within twenty minutes, it goes on the deferred list and the next one is tried. Breadth
  beats completeness; a deferred variant costs nothing.
- **Wave 3 — deferred list.** Anything that failed triage, revisited only if someone actually
  wants that map. Most will be PHP 8.4 breakage in variant classes.

The registry file is updated as part of the same change that installs a variant, never
afterwards.

### The legacy-board limitation — read this before planning any map work

This is the single most important constraint in the project and the draft spec missed it.

The modern React board hard-codes **Classic map geometry** in a TypeScript data file, and the
game object's "is this a classic game?" check whitelists exactly three variants: Classic,
Classic France vs Austria, and Classic Germany vs Italy. Everything else falls through to the
**legacy board**.

Therefore:

- **Every ported variant renders on the legacy board only.** Westeros included. This is not a
  bug to be fixed in passing; it is a property of the codebase.
- **Custom art on a PNG reskin of Classic would be invisible on the React board**, because the
  React board draws vector geometry from its own data file and never loads the variant's map
  image. A reskin done the cheap way is a reskin nobody sees on the default board.

The owner must therefore choose between two routes for story 3 (custom art):

- **A — legacy-board PNG reskin.** Cheap, well-trodden, works exactly like every community
  variant in the tree. Players see the art only if the game runs on the legacy board.
- **B — React-board fork of the Classic map data.** The art shows up on the default modern
  board, but this means forking and maintaining hard-coded geometry in the React source, and
  re-doing it after upstream board changes. This is core work, not a content job.

**Decision: deferred to the human owner.** It is a taste-and-effort trade-off, not a technical
one, and picking wrong wastes the most time of anything in this plan. Issue 010 carries it.

### Bots

The bot pack is **not part of this stack's compose file**. It lives in a **separate checkout**,
`webdiplomacy_bots_mila`, which builds its own images; the compose file's trailing comment
explains how it attaches to this stack's Docker network and calls the site's API. Seven bot
accounts with fixed API keys are created by the bot-account SQL that the installer already
runs.

- The per-game restriction option that older documentation mentions **was removed in 1.82**. The
  supported control is the **bot variant ID list** in the site config, which defaults to Classic
  plus the two Classic two-player derivatives. That is the mechanism for story 38.
- **Game-ID multiplexing is real**: the API multiplies game IDs and adds a per-key offset so one
  bot process can hold several seats. This is not a misunderstanding to be corrected.
- Gunboat is expressed as a press type of "no press" on the game.
- **Hardware requirements are unknown** and must be read out of that repository before anything
  is promised. The bot models are neural and may simply not fit this machine. Issue 004 is that
  investigation and it gates issue 005; no bot work happens until the report exists.

### Upgrades

Schema upgrades are per-version SQL scripts in the install tree, named for the version pair
they bridge. The site's header **bricks every page** when the schema version recorded in the
database does not match the code's version constant (currently 183). That is a feature — it
prevents a half-upgraded site from corrupting games — but it means an upgrade is a planned
outage with a backup taken first, never a casual `git pull`. Issue 012 writes the procedure.

### Branch strategy

`master` stays clean and tracks upstream. `local` is the deployed branch and carries this
folder, the site config, compose overrides and ported variants. Upstream is merged into `local`,
never the reverse. Nothing is ever committed to `master`.

### Phases

| Phase | Goal | Done when |
| --- | --- | --- |
| **P1** | The stack runs locally and is trustworthy. | Site answers on localhost; entrypoint log ends with the READY marker; gamemaster runs visible in the event server's logs; all four config secrets set; database on a named volume with a nightly dump and one proven restore; ten accounts exist with the owner promoted to admin; public registration refused by the web server; bot feasibility reported (005 only if that report says yes). |
| **P2** | The stack is reachable from the LAN and only the LAN. | A second device on the LAN loads the site by IP, logs in, submits an order and sees a live update; the address is stable across router reboots; every port except the web port is still bound to localhost; the host firewall admits only the LAN subnet. |
| **P3** | The named wants are playable. | Westeros installed, reviewed and passing the acceptance checklist; the two-player roster confirmed and each map passing the checklist. |
| **P4** | Breadth. | Wave 0 registered and passing; wave 2 harvested in supervised batches; the registry lists every variant with a status; a deferred list exists. |
| **P5** | Custom art. | The owner has chosen route A or B, the choice is written into this spec, and the work is either scheduled or explicitly dropped. |

## Testing Decisions

### The single seam

There is exactly one integration seam worth testing: **the running stack, over HTTP, from a
second device on the LAN.** Not the PHP classes, not the React components. This is a deployment
project; a passing unit test on an adjudicator class proves nothing about whether two friends
can play Westeros on a phone, and that is the only question that matters.

This is a deliberate choice to write **no new automated test code**. The value is in the
checklists being actually run.

### Health checks

Before any functional test, confirm the stack is alive:

1. The site's **status endpoint** reports a recent gamemaster last-run time.
2. The **entrypoint log**, served as a static text file, ends with
   `READY - webDiplomacy system initialized`.
3. The **event server's container logs** show gamemaster calls arriving.

If any of the three disagree, stop and fix that before testing anything else. A stalled
gamemaster makes every phase test look like a variant bug.

### Per-variant acceptance checklist

Every variant that is installed — ported, harvested, or merely enabled — must pass all five
before its registry status becomes `playable`:

1. **It appears on the New Game form** with the right name and player count.
2. **Its starting position matches the source image** it was ported from: same units, same
   types, same provinces, same owners. Check against the upstream variant's own map, not from
   memory.
3. **A spring move phase adjudicates**, including at least one bounce and one support order.
4. **A build phase resolves**, both a build and a disband, in the right provinces.
5. **Supply-centre counts after autumn are correct** on the scoreboard and on the map.

Anything that fails goes to the deferred list with the failure noted; it does not get
"temporarily" marked playable.

### Adjudicator regression

The site ships a **DATC test page** — the standard Diplomacy Adjudicator Test Cases, with a
batch mode. It is the regression suite for the rules engine and is run:

- once on first install, to record a baseline;
- after any upgrade;
- after any change to shared adjudicator code.

It tests Classic rules only. It will not catch a variant-specific adjudication bug, which is
what the per-variant checklist above is for. The two are complementary and neither substitutes
for the other.

### Prior art

Both tools already exist in this codebase and neither needs building: the DATC page with its
batch runner, and the status endpoint with its gamemaster health reporting. The testing plan is
to *use* them on a schedule, not to reinvent them.

### Not tested

Load, concurrency, browser compatibility beyond the devices actually in the house, and
security against a determined attacker. Two players on a LAN do not justify any of it.

## Out of Scope

- **Public hosting.** No port forwarding, no public DNS, no exposure beyond the LAN. If this
  ever changes, the database password, the registration block, and the whole security posture
  must be reconsidered from scratch.
- **TLS.** No certificate, no HTTPS. Consequence, accepted: **web push notifications require a
  secure context and are therefore lost** on a plain-HTTP LAN address. Also, the site's
  registration and password-reset links build their URL from the request host but hard-code an
  `https://` scheme, so those links come out wrong and must be hand-edited to `http://` when
  used. Neither is worth a certificate authority for two people.
- **Mobile apps and responsive redesign.** The site is used on phones as-is. Whatever the
  legacy board does on a small screen is what it does.
- **Ranking integrity.** Points, ladders and anti-cheat are irrelevant among two friends and
  are not defended.
- **Real e-mail delivery.** No outbound SMTP. Mail is read in debug output or the mail catcher.
- **Bots on non-Classic maps.** The models are trained on Classic and the config restricts them
  accordingly. Not attempted.
- **React-board support for ported variants.** Every port plays on the legacy board. This is out
  of scope unless issue 010 chooses route B, in which case it is in scope for Classic only.
- **Upstream contributions.** Fixes to upstream code may be offered, but this project is not
  responsible for getting anything merged.

## Further Notes

### Licensing

webDiplomacy is **AGPL v3**. Running a modified private fork is entirely permitted. The AGPL's
network clause means that **anyone who uses the site over the network may request the
corresponding source**, and it must be given to them. In practice that is two friends and the
occasional guest, and the answer is to hand them the `local` branch. This is a real obligation,
not a formality; it is also trivially satisfied here. It is another reason `master` stays clean
and merges cleanly — the source being handed over should be legible as "upstream plus these
changes".

### Third-party intellectual property

- **Westeros** is derived from A Song of Ice and Fire. The variant port is a fan work. Private
  LAN use is not a distribution and raises no practical issue; **publishing the map or the site
  would**.
- **Harvested community variants** carry their own authorship. Each one's author is recorded in
  its variant definition and must be preserved in the registry. Do not strip attribution.
- **Custom artwork** commissioned or drawn by the owner is the owner's; if it is ever
  contributed upstream, that is a separate and deliberate decision.
