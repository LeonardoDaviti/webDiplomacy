## How it was run

1. Logged in as `admin` (curl cookie jar, the recipe in
   [`issues/001-smoke-test.md`](issues/001-smoke-test.md)).
2. Maintenance mode **on** —
   `admincp.php?tab=Control%20Panel&actionName=maintenance`. `datc.php` renders the test harness
   only when `$Misc->Maintenance` is set, and DATC adjudication would corrupt any game processed
   at the same time.
3. Ran every case in ascending `testID` order and read the verdict from both the result page and
   `wD_DATC.status`.
4. Maintenance mode **off**; `status.php` back to green (Game Processing ✅, Maintenance Mode ✅
   Off, Error Logs 0). The only two warnings are the install's permanent ones — offsite game
   backups and last SSE client connect.

The run left ~270 files in `datc/maps/` (one large map plus a thumbnail per case). That is
expected — the directory is gitignored and `datc.php?reset=on` empties it.

### Three things that will bite whoever re-runs this

- **`datc/maps/` must be writable by the web user.** It ships owned by the host user with `755`,
  so `map.php` dies with
  `file_put_contents(datc/maps/<turn>-json.map): Failed to open stream: Permission denied`. That
  file *is* the order interface's board data (`loadBoardTurnData()`), so the failure is silent in
  the page body and shows only as `ReferenceError: loadBoardTurnData is not defined` in the
  browser console — the orders box sits on "Loading order..." for ever and the case never
  finishes. Fix with `chmod 777 datc/maps` (directory permissions are not tracked by git).
- **The page needs JavaScript; curl alone cannot run the suite.** Each case is two requests: the
  first renders an order interface and a footer script that enters the orders and POSTs them to
  `ajax.php`, the second is a self-navigation to `datc.php?DATCResults=<json>` which adjudicates
  and checks. Use a browser, or drive a headless one.
- **The second request carries no `testID`.** `datc/interactive.php` falls back to *the lowest
  `testID` whose status is still `NotPassed`*, so the results of one case are checked against
  whichever case that happens to be. Run the suite in ascending order from a clean
  `datc.php?reset=on` and it lines up. Jump to a case out of order — or keep going after a
  failure — and every later case is scored against the stale earlier one, which produces a long
  cascade of bogus failures. Two earlier attempts here reported 15–18 "failures" for exactly
  this reason before the sequencing was corrected; none of them were real.

## Re-running it

`datc.php?reset=on` first (this baseline left all 137 rows `Passed`, and the batch runner only
picks up rows that are `NotPassed`), then **Batch-test** from the first case. Compare the
pass/fail counts and the failing-ID list against the table above, and record a new
`datc-baseline-<date>-<sha>.md` after any upgrade that changes the result.
